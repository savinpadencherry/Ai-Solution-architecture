💥 Connascence — the Blast Radius Simulator

Coupling metrics count how many dependencies you have. Connascence asks a sharper question: if I change this, what else must change with it — and will anyone notice before production does? Two components are connascent when they’re “born together”: change one, the other has to follow.

Part 1 · Pull the Triggers the centerpiece

One payment service, four things touching it. Press each change trigger and watch the blast radius light up — and notice the two different kinds of pain: LOUD (the compiler screams) vs SILENT (production finds it at 3am).

Feel the pattern? The worst changes aren’t the loudest — they’re the silent ones at long distance. That’s the wholeconnascence idea: dependencies have a strength and a distance, and disasters live where strong meets far.

Part 2 · The Full Map — 9 forms of “born together” reference

Every trigger you pulled was one of these. Five live in the source code (static), four live at runtime (dynamic). Blue is weak & healthy; red is strong & dangerous.

🧾 Static — visible in the code
CoN · WEAK
Name
must agree on a name
rename() → every caller updates
CoT · MILD
Type
must agree on a type
int → decimal breaks callers
CoM · STRONG
Meaning
must agree what a value means
if (status == 1) 🤫
CoP · STRONG
Position
must agree on the order of values
charge(amount, id) — swap it 🤫
CoA · STRONGEST
Algorithm
must run the same math
mirrored hashing / discount logic
⚡ Dynamic — lives at runtime
CoE · MODERATE
Execution
must run in order
init() before process() — always
CoTt · STRONG
Timing
must answer within a deadline
settle within 30s → races
CoV · STRONG
Values
several values change together
rect.width ↔ rect.height, start ↔ end date
CoI · STRONG
Identity
must point at the same entity
both services → same customer record

Part 3 · The Two Rules & the Fix-o-matic the payoff

Connascence beats raw coupling counts because it comes with an action policy — two rules and a repair direction:

Rule 1 · The Distance Rule: weaken connascence as distance grows. Inside one class, connascence of position is fine. Across a service boundary, it’s a landmine.
Rule 2 · Refactors downgrade: every good refactoring move converts a strong form into a weak one. Watch the flips:
Position → Name
chargeCard(1999, 42)          // which is which?? 🤫
chargeCard(amount=1999, accountId=42)   // order no longer matters
Meaning → Type
if (status == 1)              // …1 means what, exactly?
if (status == Status.APPROVED)          // the meaning is now a named type
Algorithm → Shared owner
// LoyaltyService re-implements the discount math
// "we'll keep them in sync" 🤫
// both call discount-engine v2 — ONE owner of the math
Count connections? No — classify them.
Strong forms across long distances are where systems go to die.
